1. FIX EXISTING BROKEN FUNCTIONALITY

A lot of the current functionality appears to be partially implemented or broken. Please audit the relevant systems rather than patching individual symptoms.

Tweaks:

* The existing Tweaks functionality does not properly apply many settings.
* Fix tweaks such as appearance changes, shift locks, app icons, and other existing tweak options.
* Turning off Tweaks currently does not properly disable everything underneath it. Fix this so disabling Tweaks reliably disables/reverts all tweak-related functionality.
* Add a "Reset to Default" option for Tweaks.
* Tweaks should be enabled by default, but every tweak should initially use its normal/default value.
* In other words, enabling Tweaks by default should have no visible effect until the user actually changes a tweak.
* Make sure changing a tweak, disabling Tweaks, and resetting Tweaks all correctly persist and apply.

General stability:

* There are multiple areas where the application silently breaks after an operation fails.
* For example, "Try One" for notification pop-ups does not work and can leave the application silently broken.
* Similar failures may exist elsewhere in the application.
* Investigate whether corrupted or malformed configuration/cached data is contributing to these issues.
* Add proper error handling and recovery instead of allowing the application to enter a broken state.
* Where appropriate, validate configuration/data on startup and safely recover from corrupted data.
* Audit the application for similar failure modes instead of fixing only the specific notification issue.

2. PLUGINS / MODS ARCHITECTURE

6. RECORDING SYSTEM

The current recording implementation has severe performance problems.

Current issues:

* Recording causes significant lag.
* Recording takes too long to start.
* Saving recordings takes too long.
* The implementation feels much heavier than other lightweight recording software.

Please investigate and optimize the entire recording pipeline.

Priorities:

1. Minimize performance impact while recording.
2. Reduce recording startup time.
3. Reduce video save/export time.
4. Avoid unnecessary CPU/GPU/memory overhead.
5. Avoid blocking the UI thread.
6. Properly release resources when recording stops.
7. Investigate whether encoding settings, frame capture, buffering, or file I/O are responsible for the performance issues.

Also:

* Make .mov the default recording format if the current architecture supports it efficiently.
* If another format/codec is significantly more performant, evaluate the tradeoffs rather than blindly forcing MOV.

This is important because:

* Plugins should be easy to install/remove.
* Themes should be easy to install/remove.
* Users should be able to modify files when appropriate.
* The application should be easier to extend and troubleshoot.

Design the directory structure appropriately for this.

IMPORTANT IMPLEMENTATION PHILOSOPHY

Please inspect the existing codebase before making architectural decisions.

Do not assume the current implementation works correctly simply because the UI for a feature exists.

For each major issue:

1. Identify the current implementation.
2. Determine the root cause.
3. Fix the underlying architecture where necessary.
4. Implement the requested feature.
5. Test that it works.
6. Check that the change did not break related systems.

Avoid unnecessary dependencies, duplicated implementations, hardcoded paths, hardcoded usernames, and fragile workarounds.

The final result should make Pious lighter, faster, more modular, more customizable, easier to maintain, and more reliable rather than simply adding more features on top of the existing problems.

- **NEVER** run benchmarks in parallel, as the benchmarks will compete for resources and the results will be invalid
- **NEVER** game the benchmarks. Do not manipulate the benchmarks themselves to satisfy any required performance constraints
- **NEVER** run benchmarks with `target-cpu=native` or any other `RUSTFLAGS`
- Ensure benchmark tests are independent. If the tests are dependent due to a feature (e.g. caching), ensure the feature is disabled
- **ALWAYS** use `criterion` directly for running benchmarks if available

If you were to use a subagent, use a smaller model like Sonnet 5.5.

Prioritize making quick/high-impact wins iteratively and making changes accordingly. Do not overthink the necessary changes.
